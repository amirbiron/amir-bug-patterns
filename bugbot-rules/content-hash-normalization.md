# content-hash-normalization

זהה מנגנוני dedup / זיהוי-כפילויות שמבוססים על hash או השוואת מחרוזות של תוכן חיצוני, כשהנרמול לפני ההשוואה חסר או עודף. שני הקצוות נכשלים הפוך: נרמול חסר ← אותו תוכן נספר פעמיים (כפילויות); נרמול עודף ← תכנים שונים ממוזגים לאחד (אובדן/חסימה שגויה). אותו פרויקט חטף את שניהם.

## דווח כשמתקיים אחד מהבאים

1. **hash על תוכן גולמי לצורך dedup.** `hashlib.md5(post_text.encode())` על טקסט שמגיע ממקור חיצוני (scraping, API, user input) בלי פונקציית נרמול לפניו. רעש שגורם ל-hash שונה לאותו תוכן: timestamps משובצים, מוני צפיות/תגובות, תווי Unicode PUA, suffixes דינמיים של הפלטפורמה ("עוד", "See more", אליפסיס).

2. **אין פונקציית נרמול אחת מוצהרת.** הנרמול מפוזר inline בכמה מקומות (פעם `.strip()`, פעם `.lower()`) במקום `normalize_for_dedup(text)` אחת שהיא החוזה — כל call site שמנרמל אחרת יוצר את הכפילויות מחדש.

3. **נרמול אגרסיבי שממזג ישויות שונות.** הסרת query params גורפת מ-URL כשחלק מה-URLs נבדלים רק בהם — `profile.php?id=111` ו-`profile.php?id=222` הופכים לאותה ישות, וחסימת אחד חוסמת את כולם. לפני הסרת רכיב, לוודא שהוא באמת רעש ולא המזהה.

4. **אין טסט דו-כיווני לנרמול.** דרושים שני טסטים: שתי גרסאות "רועשות" של אותו תוכן ← אותו hash; ושני תכנים שונים באמת (כולל כאלה שנבדלים רק ברכיב שהנרמול נוגע בו) ← hashes שונים. טסט אחד בלי השני מכסה רק קצה אחד של הדפוס.

## False positives

- hash על תוכן פנימי דטרמיניסטי (לא scraping) — אין רעש לנרמל.
- dedup מכוון-רגישות (audit, חתימות) שבו כל byte שונה באמת נחשב שונה — שם נרמול הוא באג, לא פיצ'ר.

## חומרה

MEDIUM — כפילויות למשתמש (אותו פוסט נשלח שוב ושוב) או חסימה גורפת שגויה; מתגלה רק בפרודקשן כי נתוני הטסט נקיים מהרעש האמיתי.
