# return-value-failure-unchecked

זהה קריאות לפונקציות שמסמנות כשל בערך החזרה (`None`, `False`, `0`, `[]`,
rowcount) כשהקורא לא בודק את הערך — ובמיוחד כשהוא עוטף ב-try/except
שמניח שחריגה היא ערוץ הכשל היחיד.

## דווח כשמתקיים אחד מהבאים

1. **דגל הצלחה קבוע אחרי קריאה.** `result = save_x(...)` ומיד אחריו
   `saved = True` / `success = True` בלי תנאי על `result`, כשלפונקציה
   הנקראת יש מסלול `return None` / `return False` בכשל.

2. **try/except סביב פונקציה שלא זורקת.** הפונקציה הנקראת תופסת חריגות
   בעצמה ומחזירה ערך falsy (מוסכמת "לא זורק, מחזיר None") — וה-caller
   עוטף ב-try/except ומדווח הצלחה מחוץ ל-except. כשה-try מכיל רק את
   הקריאה הזו, ה-except למעשה לא יופעל לעולם — והכשל עובר מתחתיו.

3. **דיווח הצלחה למשתמש בלי תנאי.** הודעת ✅ / "נשמר" / "נשלח" נשלחת
   אחרי הקריאה ללא בדיקת הערך החוזר.

4. **תוצאת invalidation לא נבדקת.** `cache.delete_pattern(...)` /
   `cursor.rowcount` / `deleted_count` שערכם 0 לא מסומן ככשל — **כשלפי
   ההקשר 0 הוא כשל** (הקוד בדיוק כתב את המפתח / בחר את השורה, אז "לא
   נמחק כלום" אומר שה-invalidation החטיא). 0 לגיטימי במחיקה אופורטוניסטית
   ("נקה אם קיים") — שם אין מה לדגל.

5. **פונקציה חדשה עם ערוץ כשל לא מתועד.** דיף שמוסיף פונקציה שגם זורקת
   בחלק מהמסלולים וגם מחזירה `None` באחרים, בלי docstring שמגדיר מה
   מסמן כשל — דגל את חוסר החוזה (זה מה שמלכד את ה-caller הבא), לא את
   עצם קיום שני הערוצים.

6. **`except` בלי `logger`, ובלי הערה שאומרת למה הכשל אינו מעניין.**
   זהו הצד ההפוך של אותו דפוס: שם ערך כשל לא נבדק, כאן חריגה נתפסה ולא
   נרשמה. ‏`except: pass` / `except: return None` / `except: return False`
   בלי אחד משני אלה הוא ממצא — גם כשאין שום הודעת הצלחה למשתמש במסלול,
   וזה בדיוק החלק שהניסוח הצר פספס. בריפו אחד, ארבע מתוך תשע הבליעות
   היו מחוץ למסלול של "✅ למשתמש": ‏`delete_pattern` שיצא ב-`return 0`
   כשהקאש כבוי, שלושה `except` שקטים בחיפוש ששלחו שלושה סבבי חקירה
   למקום אחר, ‏`AttributeError` שהפך ל-`return False` במחיקה,
   ו-`try/except` שהפך 404 אמיתי לתשובה על משאב קיים.

   **והסייג, מאותו ריפו:** ההערה הזו היא גם מה שמונע את התיקון הגרוע —
   הרחבת ה-`except` כדי להעביר טסט. ראה `widened-exception-scope.md`.

## False positives

- פונקציות raise-on-error מתועדות: try/except הוא הטיפול הנכון שם.
- fire-and-forget מוצהר (מטריקות, לוגים, analytics) שכשל שקט מקובל בו.
- הערך נבדק בהמשך הזרימה (מוחזר ל-caller שבודק) — עקוב לפני דיווח.

## חומרה

HIGH — המשתמש מקבל אישור הצלחה על פעולה שנכשלה: גיבוי שלא נשמר, קאש
שלא התרענן, הודעה שלא נשלחה. הכשל שקט עד שהנתונים נחוצים — ואז מאוחר.
