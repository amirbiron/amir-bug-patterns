# logical-entity-vs-version-document

זהה פעולה שממוענת ל**מסמך** בזמן שהמשתמש התכוון ל**ישות**. כשלכל שינוי נוצרת שורה חדשה (גרסאות, היסטוריה, append-only), "הקובץ" של המשתמש הוא מפתח לוגי (`user_id` + `name`) ואילו במסד יש N מסמכים — וכל פעולה חייבת להכריע במפורש למי היא פונה.

## דווח כשמתקיים אחד מהבאים

1. **מחיקה, שיתוף, שינוי שם או שינוי הרשאה שמסננים לפי `_id` / `id` שהגיע מהממשק**, באוסף שמחזיק מספר מסמכים לאותה ישות. התסמין הקלאסי: הפריט נמחק, **וחוזר ברענון** — גרסה אחת אחורה; ופריט עם גרסה יחידה נעלם סופית, כלומר שתי ישויות שנמחקו יחד מתנהגות שונה.

2. **מטא-דאטה שמתאר את הישות ונולד מחדש בכל כתיבה** — `created_at`, בעלות, תגיות, מזהה חיצוני. אם כל מסך קורא את הגרסה האחרונה, "נוצר" מציג בפועל את זמן העריכה האחרונה.

3. **כתיבה שמתווספת להיסטוריה במסלול כשל או במסלול ברירת מחדל** — באפר ריק, "החלף" שנפל לשמירה גנרית. התוצאה: גרסה אחרונה ריקה על ישות תקינה.

4. **אחסון מפוצל.** אותה ישות יכולה לשבת בשני אוספים / טבלאות / דליים (`code_snippets` ↔ `large_files`, ‏DB ↔ object storage), ופעולה גורפת — ייצוא, מחיקה, חיפוש, אינדוקס, מיגרציה — מונה רק אחד מהם. הכשל שקט: הארכיון יוצא חסר בלי סימן.

5. **נתונים נגזרים שנשארים תלויים בגרסה שנמחקה** — צ'אנקים, אינדקס חיפוש, תמונות ממוזערות, קאש.

6. **אותה שאילתה כתובה ביותר ממקום אחד** (בוט, webapp, API), כשרק אחד מהם עובר דרך שכבת הגישה המשותפת — ראה `duplicate-rule-second-copy.md`.

## התיקון המומלץ

שאילתה שממוענת לישות מסננת לפי **מפתח הישות**, לא לפי מזהה מסמך שהגיע מהלקוח; מטא-דאטה של הישות עובר בירושה מהמסמך הראשון; וכל פעולה גורפת מונה במפורש את כל האחסונים. השאלה שחושפת את זה בסקירה: *אם למשתמש יש שלוש גרסאות של הפריט הזה, ואחת מהן באחסון השני — מה הפעולה הזו עושה?*

## False positives

- פעולות שבאמת ממוענות לגרסה — "שחזר גרסה 3", "הצג diff", מחיקת גרסה בודדת מתפריט ההיסטוריה.
- אוסף שבו מסמך = ישות, בלי היסטוריה.

## חומרה

HIGH — אובדן נתונים או תחיית נתונים, שניהם בלי הודעת שגיאה.
