# מדיניות שהדפדפן אוכף — והשרת לא רואה

**מתי להחיל:** כל אפליקציה שמגישה HTML, מגדירה CSP, `SameSite`, CORS,
או משתמשת ב-`postMessage` / iframes / OAuth בדפדפן.

**המכנה המשותף:** האכיפה קורית **בצד הלקוח**. כשהיא חוסמת משהו,
בקשת האפליקציה לא מגיעה לשרת — אין `403`, אין לוג, אין שום עקבה
בנתיב שציפינו לה. מבחוץ זה נראה בדיוק כמו כפתור שבור.

זה מה שהופך את המשפחה הזו למסוכנת: **כל כלי ה-debug הרגילים מראים
"הכול תקין"**, כי מבחינת ה-endpoint באמת לא קרה כלום.

**שני ערוצי אבחון, בסדר הזה:**

1. **הקונסול של הדפדפן** — תמיד שם, בלי הגדרה מוקדמת. זה המקום שבו
   ההודעה מופיעה במלואה.
2. **דיווחי CSP** — אם הוגדר `report-to` (או `report-uri` הישן),
   הדפדפן שולח דוח הפרה ל-endpoint נפרד. זה כן מגיע לשרת, ולכן שווה
   להגדיר מראש: בלעדיו אין שום סיכוי לגלות חסימות אצל משתמשים
   שלא ידווחו.

**ולפני הכול — למנות את הדפים שנגישים בלי התחברות.** שם טעות מדיניות
פוגעת במי שאינו מחובר, ואין סשן מאומת שדרכו אפשר לעקוב אחריה. הרשימה
אינה "כל מה שנראה ציבורי": ב-CodeBot, למשל, הדפים הציבוריים הם
`/share/<share_id>`, `/share/<share_id>/download`, `/shared/<token>` ו-
`/shared/styled/<token>` — ואילו ה-API שמייצר את הקישורים עצמו דורש
התחברות. הדמיון בשמות אינו מעיד על ההרשאה.

## B1. מדיניות גורפת שנכתבה לפי הרוב, חונקת מקרה יחיד

**חומרה:** HIGH — כשל שקט לחלוטין

### איך זה נראה

הנחיה מסוג `'none'` נכתבת פעם אחת, כשהמקרה החריג עוד לא קיים. היא
נכונה ביום שנכתבה. חודשים אחר כך מישהו מוסיף את המקרה החריג — ולא
יודע שהמדיניות קיימת.

### דוגמה אמיתית

**Markdown-Docs (#21):** ה-CSP כלל `form-action 'none'`, כי האפליקציה
היא SPA בלי טפסי HTML. ואז נוסף **טופס אחד** — מסך אישור ה-OAuth.
הדפדפן בלע את הלחיצה:

```text
Refused to send form data to '/mcp-consent' because it violates
the following Content Security Policy directive: "form-action 'none'".
```

בשרת לא הופיע כלום. הבקשה מעולם לא נשלחה. ארבע בדיקות שרת עברו.

### המשפחה המלאה

| הנחיה | מה נשבר בשקט |
|---|---|
| `form-action 'none'` | טופס HTML יחיד באפליקציית SPA |
| `SameSite=Strict` | חזרה מ-OAuth של ספק חיצוני |
| `connect-src 'self'` | `fetch` ראשון לדומיין חיצוני |
| `frame-ancestors 'none'` | הטמעה לגיטימית שנוספה מאוחר |
| `img-src 'self'` | אווטאר או תמונה מ-CDN |
| allowlist של CORS | סביבת preview חדשה |
| `Permissions-Policy` | מיקרופון/מצלמה בפיצ'ר חדש |

### כלל לזיהוי

1. הנחיית CSP עם `'none'` בפרויקט שמגיש HTML — לדרוש הערה שאומרת
   **איפה ההיתר יינתן** כשהמקרה החריג יגיע, לא רק "אנחנו לא משתמשים".
2. תגובת HTML שמכילה `<form>`, `<iframe>`, או `fetch` לדומיין חיצוני,
   באפליקציה שיש לה CSP גלובלי — לוודא שההנחיה הרלוונטית מתירה אותה.
3. פיצ'ר שנכשל **בלי שום עקבה בשרת** — לבדוק מדיניות לפני שמחפשים
   באג בקוד.

### התיקון המומלץ

היתר **פר-תגובה**, לא הרפיה גלובלית. מידלוור כותרות שמוסיף
את המדיניות הגלובלית **אחרי** ה-handler, ורק אם היא חסרה:

```python
@app.middleware("http")
async def security_headers(request, call_next):
    response = await call_next(request)          # ה-handler רץ קודם
    for header, value in SECURITY_HEADERS.items():
        response.headers.setdefault(header, value)   # לא דורס מה שהדף הביא
```

**הסדר הוא מה שמכריע, לא `setdefault` לבדו.** ה-handler רץ ראשון,
ולכן כשהמידלוור מגיע הכותרת של הדף כבר שם ו-`setdefault` מדלג עליה.
מידלוור שרץ **לפני** ה-handler, או שמשתמש ב-`append`, ייצור **שתי
כותרות CSP** — והדפדפן אוכף את שתיהן, כלומר את החיתוך המחמיר שלהן.
התוצאה זהה לחסימה מלאה, וקשה יותר לאבחון.

**איך מוודאים:** ב-DevTools → Network → Headers, לספור את מופעי
`content-security-policy` בתגובה. יותר מאחד הוא הבאג.

והמדיניות של אותו דף צריכה להיות **מחמירה מהגלובלית** בכל כיוון אחר,
ומרפה רק במה שהדף באמת עושה. דף עצמאי בלי JS יכול לקבל
`default-src 'none'` ובלי `script-src` בכלל.

### False positives

- שירות API בלי HTML — CSP לא רלוונטי.
- הנחיה שבאמת אין לה מקרה חריג בפרויקט.

## B2. ערך פגום בהנחיית מדיניות גרוע מערך חסר

**חומרה:** MEDIUM
**קשור ל-`CORE-PATTERNS.md` U3**, בזווית של דקדוק

### איך זה נראה

בונים הנחיית מדיניות ממחרוזת חיצונית. הערך אינו חוקי בדקדוק היעד.
הדפדפן פוסל את ההנחיה — ואז **הפיצ'ר חסום לגמרי**, כאילו כתבנו
`'none'`.

### דוגמה אמיתית

**Markdown-Docs (#21):** בניית `form-action` מ-`redirect_uri` של לקוח
שנרשם דרך Dynamic Client Registration:

```python
return f"{parsed.scheme}://{parsed.netloc}"   # שגוי
```

`netloc` כולל פרטי הזדהות. `https://user:pass@host` אינו
`host-source` חוקי. הרישום פתוח לכל דורש, ולכן זה קלט ממשי.

הגרסה השנייה חתכה userinfo אבל החזירה IPv6 בסוגריים — **גם שגוי.**
הדקדוק אינו מגדיר `IP-literal` כלל:

```abnf
host-part = "*" / [ "*." ] 1*host-char *( "." 1*host-char) [ "." ]
host-char = ALPHA / DIGIT / "-"
```

### כלל לזיהוי

1. f-string או קונקטנציה שמכניסים ערך חיצוני לתוך `Content-Security-Policy`,
   `Set-Cookie`, `Location`, או כל כותרת אחרת.
2. שימוש ב-`urlsplit(...).netloc` לבניית origin — הוא כולל userinfo.
   `hostname` ו-`port` בנפרד, ואז אימות.
3. ניקוי תווים אסורים (blocklist) במקום אימות מול הדקדוק (allowlist).

### התיקון המומלץ

**allowlist מול הדקדוק, לא blocklist של תווים.** רשימת מה שאסור לעולם
אינה שלמה. עבור `host-source`:

```python
_CSP_HOST = re.compile(r"[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)*\.?")

if not host or not _CSP_HOST.fullmatch(host):   # fullmatch, לא match
    return ""
```

**חובה `fullmatch` (או עיגון ב-`\A...\Z`).** `match` בודק רק את
ההתחלה, ולכן `example.com evil;script-src *` היה עובר את הבדיקה עם
prefix תקין וסיומת שמזריקה הנחיה שלמה. זו טעות שהופכת את ה-allowlist
לחסר ערך בדיוק במקרה שהוא נועד לתפוס.

וכל מה שלא תואם — **מושמט**, לא נדחף פגום. נופלים מעצמם: userinfo,
IPv6, דומיין לא-ASCII, רווח, ו-`;` שגם מפצל את הכותרת עצמה.

## B3. הפניה בולעת את הכותרות שהתשובה נשענת עליהן

**חומרה:** MEDIUM

### איך זה נראה

נתיב מחזיר `3xx` לפני שהוא מגיע ל-handler שמייצר את הכותרת. הלקוח
רואה את ההפניה, לא את הכותרת, ולא יודע מה נדרש ממנו.

### דוגמה אמיתית

**Markdown-Docs (#19):** `Mount` של Starlette רושם `^/mcp/(?P<path>.*)$`.
בקשה ל-`/mcp` בלי לוכסן מקבלת `307` ל-`/mcp/`. ההפניה **אינה נושאת
`WWW-Authenticate`** — הלקוח לא ראה אתגר אימות ולא התחיל OAuth.

### כלל לזיהוי

1. נתיב שמחזיר `401` / `429` / `3xx` עם כותרת משמעותית
   (`WWW-Authenticate`, `Retry-After`, `Location`), שיושב מאחורי
   `Mount` / rewrite / trailing-slash redirect.
2. `app.mount(path, sub)` — לוודא ש-`path` בלי לוכסן נענה ישירות ולא
   דרך `307`.

### התיקון המומלץ

נתיב שכל ערכו בכותרת חייב לענות **ישירות**. אם ההרכבה מייצרת הפניה,
לרשום את הצורה בלי לוכסן במפורש ולהעביר את הבקשה פנימה — לא להפנות.

מלכודת: העברה שממחזרת רק את ה-endpoint הפנימי מדלגת על מידלוור
האימות של תת-האפליקציה. התוצאה נראית נכונה (`401` תקין) אבל **דוחה
טוקנים תקפים**. יש להעביר לאפליקציה כולה.

## B4. נכס סטטי בכתובת קבועה מול `max-age` ארוך

**חומרה:** MEDIUM — הדפדפן מגיש קוד שלפני הדיפלוי, **עד שנה**, ואין שום עקבה בשרת

### איך זה נראה

`max-age` ארוך ומזהה גרסה בכתובת הם **החלטה אחת**, ונכתבים בשני מקומות שונים: הראשון בקונפיג של השרת, השני בתבנית. תבנית אחת ששכחה את המזהה יורשת את התקרה של כולן.

### דוגמה אמיתית

**CodeBot (PR #3283):** `md_preview.html` טען את `sticky-notes.js` ואת `sticky-notes.css` בכתובת קבועה, בלי `?v={{ static_version }}` — שתי התגיות היחידות של הפתקים בכל הריפו בלי buster. מול `SEND_FILE_MAX_AGE_DEFAULT=31536000` הדפדפן הגיש את העותק שנשמר לפני הדיפלוי, בלי revalidation. התסמין: רינדור המארקדאון בפתקי קבצים הפסיק לעבוד אחרי דיפלוי, **בזמן שאותו קוד בדיוק עבד בלוחות** — כלומר שני מסלולים לאותו קובץ, ורק אחד מהם עדכני.

**Campaign AI (`#141`), מהצד ההפוך:** `SPAStaticFiles` הגיש את הפרונטאנד בלי `Cache-Control` (רק ETag/Last-Modified) והשמות בלי hashing — כלומר אותה החלטה חסרה, רק שכאן היא נפלה לצד של "בלי מדיניות".

### כלל לזיהוי

1. תגית `<script>` או `<link>` שנוספת לתבנית **בלי** מזהה הגרסה שכל שאר התגיות באותו פרויקט נושאות. הבדיקה היא `grep` על שתי הצורות וספירה — תגית אחת חריגה היא הממצא.
2. `SEND_FILE_MAX_AGE_DEFAULT` / `max-age` מעל כמה דקות, בפרויקט שמגיש נכסים בשמות קבועים.
3. Service worker או manifest שמוגשים עם `max-age` — הם בדיוק הקבצים שצריכים להתעדכן ראשונים.

### התיקון המומלץ

`max-age` ארוך מותר **רק** לכתובת שמשתנה כשהתוכן משתנה: hash בשם הקובץ, או `?v=<גרסה>` שנגזר מהבנייה. כתובת קבועה מקבלת revalidation (`no-cache` + `ETag`), לא `no-store`. ומכיוון שזו החלטה בשני מקומות — טסט שסורק את התבניות ומוודא שכל תגית נושאת מזהה עדיף על משמעת.

## B5. מדיניות cache גורפת שדורסת מנגנון שנבנה בכוונה

**חומרה:** MEDIUM

### איך זה נראה

מידלוור שכותב כותרת cache על **כל** תגובה מסוג מסוים, בדריסה ולא כברירת מחדל. הוא מבטל בדיוק את המקרים שמישהו טרח לכוון.

### דוגמה אמיתית

**CodeBot (PR #2932):** `_disable_html_cache` דרס כל תגובת HTML ב-`no-cache, no-store, must-revalidate` — כולל עמודים שמגדירים `ETag` במפורש. מנגנון ה-revalidation שנבנה לעמודים הכבדים פשוט לא עבד, והדפדפן הוריד הכול מחדש בכל פעם.

### כלל לזיהוי

`after_request` / מידלוור שמשים `response.headers["Cache-Control"] = ...` בהשמה על סוג תוכן שלם. השאלה: **האם handler בודד יכול לקבוע מדיניות משלו?** אם לא — זו דריסה.

### התיקון המומלץ

`setdefault` ולא השמה, בדיוק כמו ב-B1: המידלוור נותן את ברירת המחדל, וה-handler שיודע יותר גובר. ואם אי אפשר — רשימת פטור מפורשת, עם הערה שאומרת מי נמצא בה ולמה.
